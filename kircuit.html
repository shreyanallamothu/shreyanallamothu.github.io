KlossyKollective

A full-stack community hub for KWK members and alumni

Role: AI Build Lab Fellow React Next.js TypeScript PostgreSQL

The problem

Kode with Klossy alumni lose touch with each other and the program after their summer ends. There's no shared space to keep collaborating, and organizers have no single tool to run community programming beyond emails.

Product objectives

  1. Centralize member experience with a single destination for events, resources, and community updates.
  2. Strengthen community connections by making it easy for members to discover interest-based communities.
  3. Support lifelong engagement by providing alumni with an ongoing space to network and stay connected with Kode with Klossy.

Feature deep dive: creating a resource

  1. Open form

    The community page displays NewResourceForm, a client-side React component.

  2. Submit

    Upon submission, the form converts its data into JSON and sends a POST request to the /api/resources route handler.

  3. Validate

    Try-catch blocks validate required fields, ensure the URL is valid, and query the database to verify the specified community exists.

  4. Save

    Drizzle ORM inserts the resource into the PostgreSQL "resources" table.

  5. Refresh

    router.refresh() reloads the server data to display the newly added resource.

Product architecture

Client

React client components handle user input: clicks, form state, filtering.

Next.js server

Server components fetch and render page data. Route handlers validate requests and process database operations.

Drizzle ORM

Translates TypeScript operations into SQL against the schema.

PostgreSQL

Stores users, communities, posts, comments, and profiles permanently.

Product decisions & tradeoffs

Determining core features

Depth > breadth

I prioritized the core experience—publishing posts, sharing resources, and organizing events—over features such as notifications, private messaging, and recommendation algorithms in an MVP.

Tradeoff: this kept the product focused to ensure it could validate whether users found the central community hub valuable. However, it also means the current product may have lower long-term engagement and stickiness as its user base grows.

Structuring community routing

Routing that scales

We used one dynamic route based on each community's slug, such as /coding-club, rather than creating a separate page in the codebase for every community.

Tradeoff: this made KlossyKollective scalable, as new communities automatically receive their own page. However, slugs must be unique and carefully validated, and changing a slug can break saved links unless redirects are implemented, increasing maintenance complexity over time.
